Building a Safer Git Client for Large Repositories

GitCat began with a problem I encountered during my internship: working in a large repository with many branches and submodules could make everyday Git operations feel slow. Switching context in our existing client meant waiting for history to reload and using memory that our work laptops could not spare.

I started with a small tool called Cherry-Pick Helper. As teammates tried it, reported bugs, and asked for more workflows, it grew into GitCat, an open-source desktop Git client built with Tauri, Rust, and Svelte.

Two ideas shaped the project. The first was responsiveness. GitCat uses git2 to read repository history, Rust to lay out the commit graph, and a virtualized canvas to draw the visible portion. This taught me that fast repository access and fast rendering are separate problems: optimizing one does not automatically fix the other.

The second was recovery. Before everyday history-changing operations, GitCat’s Safety Manager records HEAD and local branch tips so those references can be restored with Undo. The snapshot does not cover all uncommitted work, and some operations have separate backup or confirmation flows. I wanted recovery to be part of the design, while being clear about its limits.

The project also has a personality: Tama, the cat, responds to real states such as searching, conflicts, and recovery. Claude Code helped accelerate implementation, while I chose the workflows and safety boundaries, reviewed changes, and tested and maintained the result.

GitCat reminded me that a useful project can start with one frustrating workflow. Listening to the people using it, understanding the problem, and improving it step by step can turn a small helper into something much more useful.
